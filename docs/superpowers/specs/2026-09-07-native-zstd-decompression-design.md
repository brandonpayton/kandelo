# Native zstd decompression on spidermonkey-node (Milestone 2 Phase I) — Design

**Status:** Approved design pending user review; implementation not started
**Date:** 2026-09-07

## Why

After Phase H, headless `claude -p` executes into the application and dies at:

```
Error: embedded text asset is missing or corrupt
  chunk-cd704anb.js:11
```

The Claude Code app ships text assets (docs, prompts, skills) as **zstd-
compressed embedded assets**. At runtime it reads the asset bytes, detects the
zstd magic (`28 B5 2F FD`), and decompresses via **`Bun.zstdDecompressSync`**
(sync) / **`Bun.zstdDecompress`** (async), then `.toString("utf8")`. Any failure
is wrapped as "embedded text asset is missing or corrupt".

The asset itself is fine — `bun-extract` already writes every module-table
entry, assets included, with bytes preserved. The gap is that there is **no
zstd decoder in the guest**: node.wasm's native seam (patch 0012) exposes zlib
(deflate/inflate/gzip/gunzip) but not zstd; node-compat's
`zlib.createZstdDecompress` is a `_notImpl` stub (Phase E); and the bun-run
`Bun` shim has no `zstdDecompress*`.

This phase adds **native zstd decompression** to spidermonkey-node — the
faithful, platform-consistent mechanism (node.wasm already links zlib the same
way), so any consumer (`Bun.zstd*`, Node's `zlib` zstd, the app's asset
reader) gets a real decoder. Confirmed feasible by a spike: zstd's decode code
compiles clean for wasm32 with the target toolchain.

## Principle

Use the normal platform path — a real linked library, exactly as `zlib`,
`openssl`, and `libcxx` are linked into node.wasm — not a bundled JS decoder.
No app-shaped compromise. Compress is out of scope (the app only decompresses
assets); the unimplemented compress side stays an honest, documented not-impl,
never a silent no-op.

## Feasibility established (spike)

The zstd single-file **decompress-only** amalgamation
(`packages/registry/zstd/zstd-src/build/single_file_libs/`, generated by
`create_single_file_decoder.sh` → `zstddeclib.c`, ~22k lines, portable C, no
x86 asm) compiled clean for wasm32 with `wasm32posix-cc` (clang 21.1.7 — the
build's own toolchain), producing a valid object. Linking is a mechanical
mirror of the existing zlib wiring; runtime `ZSTD_decompress` is standard,
portable, and confirmed at the implementation's build+test.

## Design

### Component 1 — a `libzstd` (decompress) library dependency

Add a `kind = "library"` package (`packages/registry/libzstd/`, named to avoid
the existing `zstd` *program* package) that mirrors `packages/registry/zlib/`:

- `package.toml`: `kind = "library"`, pinned to the same in-tree zstd source
  version (1.5.6), `[outputs] libs = ["lib/libzstd.a"]`,
  `headers = ["include/zstd.h"]`.
- `build-libzstd.sh`: generate the decompress-only amalgamation from the pinned
  zstd source (`create_single_file_decoder.sh`), compile it with the worktree
  SDK toolchain to `lib/libzstd.a`, and install `zstd.h` (from
  `zstd-src/lib/zstd.h`) into `include/`. Decompress-only keeps the archive
  small; the decode-only amalgamation is the proven-compiling source.

This makes the library resolvable via `cargo xtask build-deps resolve libzstd`,
exactly like `zlib`.

### Component 2 — link it into the SpiderMonkey build

In `packages/registry/spidermonkey/build-spidermonkey.sh`, mirror the zlib
block:
- resolve the dep (`ZSTD_PREFIX="$(resolve_dep libzstd)"`), assert
  `$ZSTD_PREFIX/lib/libzstd.a` and `$ZSTD_PREFIX/include` exist;
- add `libzstd` to the build-deps list (the `libcxx openssl zlib` line);
- add `$ZSTD_PREFIX/lib/libzstd.a` to `LDFLAGS` and `-I$ZSTD_PREFIX/include`
  to `CFLAGS`/`CXXFLAGS` (right beside the zlib entries).

### Component 3 — the C seam (new sequential patch `0021`)

In `js/src/shell/js.cpp`, add `#include <zstd.h>` (an angle-bracket third-party
include — place it in the correct style-check group; the zlib seam's
`#include <zlib.h>` in patch 0012 is the precedent) and a self-contained native
(added before `DefineKandeloNodeNative`, so it uses only public/`<zstd.h>`
symbols):

`__kandeloZstdDecompress(bytes)` — takes a `Uint8Array`/`ArrayBuffer`, returns a
new `Uint8Array` of the decompressed bytes:
1. `ZSTD_getFrameContentSize(src, srcLen)`; if a valid known size, allocate that
   and `ZSTD_decompress` once.
2. If `ZSTD_CONTENTSIZE_UNKNOWN`, decode with a streaming loop
   (`ZSTD_createDStream`/`ZSTD_decompressStream`) into a growable buffer.
3. `ZSTD_CONTENTSIZE_ERROR` or a `ZSTD_isError` result → throw a clear
   `Error("zstd decompression failed: <ZSTD_getErrorName>")` (fail loud, never
   return partial/garbage).

Register it in `DefineKandeloNodeNative` and **delegate it through
`packages/registry/spidermonkey/node-compat/adapter.js`'s `_nodeNative`
whitelist** (an undelegated native is `undefined` to bootstrap.js — the
recurring gotcha).

### Component 4 — `Bun.zstd*` in the bun-run shim

In `runtime/bun-run/bun-run.js`, add to the `Bun` global:
- `zstdDecompressSync(bytes)` → `_nodeNative.__kandeloZstdDecompress(bytes)`
  wrapped as a `Buffer`/`Uint8Array` (Node's `Buffer` is available).
- `zstdDecompress(bytes)` → `Promise.resolve(zstdDecompressSync(bytes))`
  (async wrapper over the sync decode; the underlying decode is synchronous —
  faithful enough, and the app awaits it).
- Compress (`zstdCompressSync`/`zstdCompress`) remain the `ni(...)` honest
  throwers (out of scope); document.

Note: `_nodeNative` is not exposed to the app; the shim reaches it the same way
node-compat already does. If bun-run.js has no `_nodeNative` handle, expose the
seam through the node-compat surface the shim already imports (e.g. call it via
`require("zlib")`'s new zstd entry, Component 5) rather than a fresh global.

### Component 5 — graduate node-compat `zlib` zstd (folded in, since the seam exists)

In `packages/registry/node-compat/bootstrap.js`, replace the
`zlib.createZstdDecompress` `_notImpl` stub with a real decode Transform over
the seam, and add `zlib.zstdDecompressSync(buf)` (Node 22+ `zlib` zstd API),
both backed by `_nodeNative.__kandeloZstdDecompress`. This is the natural home
for the seam on the Node side and gives bun-run.js a stable path to it
(`require("zlib").zstdDecompressSync`). Compress-side zstd (`createZstdCompress`
/`zstdCompressSync`) stays an honest not-impl.

**Preferred `Bun.zstd*` routing:** to avoid a fresh `_nodeNative` handle in
bun-run.js, `Bun.zstdDecompressSync`/`zstdDecompress` call
`require("zlib").zstdDecompressSync` (Component 5) — one code path, no new
global — superseding Component 4's direct-`_nodeNative` note.

## Testing (durable — extends `host/test/esm-probe-guest.test.ts` or a small new host test)

In-kernel, self-contained:
1. **Known-blob decode:** a small text string compressed to a committed zstd
   blob (hex/base64 constant in the test) decodes via
   `zlib.zstdDecompressSync` / `Bun.zstdDecompressSync` back to the exact text.
2. **Frame-content-size-unknown path** (a streamed/no-size frame) decodes
   correctly (if easy to produce; else note the streaming path is covered by
   the acceptance run against real assets).
3. **Corrupt input fails loud** — a truncated/garbage zstd frame throws
   `"zstd decompression failed"`, not silent/partial output.
4. Regression: all Phase A–H esm-probe cases stay green.

## Rebuild & acceptance (Phase J seed)

One `node.wasm` rebuild after the library dep + build wiring + seam + shim +
bootstrap edits (the library dep also builds once). Acceptance: the new tests
green, no regression, and a throwaway `claude -p` (isolated config, dummy key,
`enableTcpNetwork`, `CLAUDE_BUN_ELF`) gets **past** "embedded text asset is
missing or corrupt"; report the next blocker verbatim as the Phase J seed.
Record native zstd decompression (and the compress-side not-impl) in
`docs/posix-status.md`.

## Risks

- **Library-build integration.** A new `kind="library"` dep + `build-deps`
  wiring + `build-spidermonkey.sh` LDFLAGS/CFLAGS edits; the decode amalgamation
  is proven to compile, and the link mirrors zlib exactly. Mitigation: verify
  the dep resolves and the shell links before/at the implementation build; the
  build fails loud on a missing `.a`.
- **`_nodeNative` reach from bun-run.js.** The shim may not have a `_nodeNative`
  handle. Mitigation: route `Bun.zstd*` through `require("zlib").zstdDecompressSync`
  (Component 5), which node-compat exposes — no new global, one code path.
- **Frame content size unknown.** Bun's embedded assets likely carry the size,
  but the streaming path must exist and be correct. Mitigation: implement and
  test the streaming branch; corrupt-input test guards the error path.
- **Include-order style check** on `#include <zstd.h>` (misc tier). Mitigation:
  place it per the checker's grouping (precedent: `<zlib.h>` in patch 0012).
- **Sequential patch / build mechanics / adapter delegation** — as in all prior
  phases (author C via real diff against post-0020; verify apply; delegate every
  native; redirect build log to a file).
- **Rebuild cost** — ~35 min; batch all edits into one rebuild.
